Workflow

Workflow config upserts and applies, and the server options clients read

Create or update a phenix config for a workflow branch

Creates the config if it does not exist and updates it otherwise. The server sets BRANCH_NAME to the branch before parsing the body, so ${BRANCH_NAME} placeholders expand to the branch name. The Content-Type header must be exactly application/json or application/x-yaml. A Topology is also checked for a node an experiment could not use, such as a hostname used twice or a reserved hostname, before it is stored. With dryRun=true it runs the same checks, returns what it would do, and stores nothing.

For an Experiment config only the schema is checked; the experiment checks run when the config is stored. The parameter's name is matched exactly, so a request that spells it differently is carried out for real.

Apply a phenix workflow config to a workflow branch

Validates the workflow config against the Workflow schema, finds the experiment mapped to the branch (phenix.workflow/branch annotation), plans an action, and checks the default bridge and the topology and scenario the action would use, including a stored topology's nodes, as creating an experiment would. Only then does it create, update, start, or restart the experiment. A failed check leaves a running experiment running. With dryRun=true the plan is returned after the same checks, and nothing is changed; a dry run before a first deploy names the configs the caller will store with pending. The server sets BRANCH_NAME to the branch before parsing the body. The Content-Type header must be exactly application/json or application/x-yaml.

path Parameters
branch
required
string

workflow branch name

query Parameters
tag
Array of strings

key=value tag stored on the experiment, joined with commas into the phenix.workflow/tags annotation; repeat the parameter for more tags

dryRun
boolean
Default: false

Runs every check, a stored topology's node checks included, and returns the plan without creating, updating, starting, or stopping anything. The parameter's name is matched exactly, so a request that spells it differently is treated as a real apply, and refused with 400 when it also carries pending.

pending
Array of strings

A config the caller will create or update before the real apply, usually the pending value a dry run of POST /workflow/configs/{branch} returned: /, such as Topology/helloworld, optionally followed by "?" and the config's references, such as Scenario/helloworld?from=helloworld-base&topology=helloworld (url-encode the value). The kind may be in any case. Repeat the parameter for more configs. A pending topology or scenario is not looked up, decoded or merged, so a first deploy can be checked before its configs are stored; the references listed after "?" are checked instead, with the errors the real apply gives (on a create, a scenario's topology annotation; each fromScenario, which must be pending or stored and annotated for the topology; each included topology, which must be pending, stored or a file on the server). An include that is neither pending nor stored is looked up as a file on the server, as the real apply does, so the answer shows whether that path exists on the server; grant workflow:create only to roles trusted with that (the default policies give it to Global Admin only). Only allowed with dryRun=true; otherwise, or for a value that is not a config name, the request is a 400.

expect
string
Enum: "none" "create" "createAndStart" "update" "updateAndStart" "restart"

The action the caller expects, usually the action a previous dry run returned. If the server plans a different action, it returns 409 and changes nothing. It is checked on dry runs as well as real applies. A value that is not an action is a 400 with the message invalid expect value "" and the cause unknown workflow action "".

Request Body schema:
required

phenix workflow config

apiVersion
required
string (API Version)
Value: "phenix.sandia.gov/v0"

The config API version; a workflow config is phenix.sandia.gov/v0.

kind
required
string (Kind)
Value: "Workflow"

The config kind, which is always Workflow.

metadata
object or null (Metadata)

Not read by the server; it is accepted so a workflow config has the same four top-level keys as every other phenix config, and so a later version can carry a name or annotations without a breaking change.

required
object (Workflow Spec)

What an apply may do and the experiment settings it sets; an empty spec applies every default.

Get server-side options

Server-side settings that clients read: every phenix CLI command fetches them over the unix socket when it starts, to inherit the server's bridge-mode, deploy-mode and use-gre-mesh, and the web UI's Experiments page reads them too. workflow-dry-run is true when POST /workflow/configs/{branch} and POST /workflow/apply/{branch} both support dryRun, and apply supports pending and expect. An older server ignores dryRun on /workflow/configs/{branch} and stores the config, so phenix workflow apply refuses servers without it.
