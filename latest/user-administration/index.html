    User Authn/Authz in phenix¶

    phenix provides three separate modes of user authentication (authn) and authorization (authz).

    • disabled
    • enabled
    • proxy

    disabled Mode¶

    When in disabled mode, no user authentication or authorization occurs. Users do not have to authenticate, and all actions are allowed.

    To use disabled mode, the UI should be built with VITE_AUTH=disabled (if Docker is being used to build the UI, use Docker build arg PHENIX_WEB_AUTH=disabled) and the UI server should be started without the -k/--jwt-signing-key option set.

    enabled Mode¶

    When in enabled mode, user authentication and authorization occurs within phenix directly. Users have to authenticate to the phenix UI, and certain actions are prohibited based on the role assigned to the user.

    To use enabled mode, the UI should be built with VITE_AUTH=enabled (if Docker is being used to build the UI, use Docker build arg PHENIX_WEB_AUTH=enabled) and the UI server should be started with the -k/--jwt-signing-key (and optionally the --jwt-lifetime) option set.

    proxy Mode¶

    When in proxy mode, user authentication is expected to occur in a reverse proxy that sits in front of phenix but user authorization still occurs within phenix directly. Users authenticate to the proxy, and certain actions are prohibited based on the role assigned to the user.

    To use proxy mode, the UI should be built with VITE_AUTH=proxy (if Docker is being used to build the UI, use Docker build arg PHENIX_WEB_AUTH=proxy) and the UI server should be started with the -k/--jwt-signing-key and --proxy-auth-header (and optionally the --jwt-lifetime) options set.

    In addition, the reverse proxy should add a header to requests being proxied that contains the username of the authenticated user, with the name of the header matching what --proxy-auth-header is set to (for example, --proxy-auth-header=X-phenix-user).

    If a user is able to authenticate to the proxy but is not yet a user in phenix, the UI shows them a sign-up page with their username. After they submit it, they are added as a phenix user and assigned the Disabled role that will deny all actions until an admin user can assign them a different role.

    Create a new user¶

    There are three primary ways to create new users. A username must start with a letter or digit and contain only letters, digits, ., _, @, + and -. phenix refuses other usernames and stores no user.

    1. Choose the Create Account link off the login page and complete all fields in the Create a New Account dialogue. This will initiate a message to an administrator's account who can then activate the account, setting the role(s) and resource name(s).

    2. From the Users page in the Admin menu, click the + button to create a new user. Here the administrator will add the role(s) and resource name(s). phenix refuses a username that is already taken or a role that does not exist, and stores no user.

    3. Create a YAML or JSON file at /etc/phenix/users.[yml|json] with the following structure. When the phenix UI starts, it looks for this file and adds any users present in the file that are not already present in phenix. For users in the file that already exist, phenix ensures the user role matches what's in the file and updates it as necessary. This file is also automatically watched, so any users added to the file while phenix is running will automatically be added to phenix. An entry may end with resource names that scope the role, each after its own :. phenix skips and logs an entry whose role does not exist, and stores no user for it.

    ui:
  users:
    - <username>:<password>:<role-name>[:<resource-name>...]
    - ...

    Login¶

    The login page is self-descriptive. Using the Remember me checkbox will set a token to local storage so that you can remove the requirement to enter a Username and Password each time the page or site is reloaded.

    If an administrator starts the UI server with the following command, authentication is enabled:

    phenix ui -k <some_string>

    Without the -k (or --jwt-signing-key), authentication is disabled.

    Generating User Authentication Tokens¶

    From the Users page in the Admin menu, click the key icon next to the given user's name. The icon shows for your own user, and for another user only when your role has users/tokens create on them. A dialog box will pop up where you can enter in a description for the token to be created and an expiration date. This expiration date should be entered in Golang time duration. For example, 4320h is valid and represents 4320 hours or about 6 months. After clicking Create Token a token should appear with the expiration date.

    This token can be used to authenticate when using the Phenix API. Specifically, you would include the following as a header in HTTP requests.

    X-Phenix-Auth-Token: Bearer ******

    On the phēnix server itself, phenix admin token create prints a token for a user, signed by the running phenix ui. --lifetime takes a duration such as 12h, or a whole number of days.

    TOKEN=$(phenix admin token create ci-bot --lifetime 30 --description "CI runner")

    User Administration¶

    The Users link in the Admin menu shows for a role with users list, or with users get on your own user, which then lists only you.

    Updating Users¶

    An administrator is able to click on the username on the table on the Users page to update a user. They can update First Name or Last Name, Role, Experiment Names, and Resource Name(s).

    Roles¶

    Global Admin is the administrator level account and has access to all capabilities, to include user management. Global Admins also have access to all resources. The following table provides a high-level overview of all the available roles and their access rights.

    Role Limits List Get Create Update Patch Delete
    Global Admin Can see and control absolutely anything/everything. E V U E V U E V U E V U E V U E V U
    Global Viewer Can see absolutely anything/everything, but cannot make any changes. E V U E V U
    Experiment Admin Can see and control anything/everything for assigned experiments, including VMs, but cannot create new experiments. E V E V V E V V E* V
    Experiment User Can see assigned experiments, and can control VMs within assigned experiments, but cannot modify experiments themselves. E V E V V
    Experiment Viewer Can see assigned experiments and VMs within assigned experiments, but cannot modify or control experiments or VMs. E V E V
    VM Admin Can see assigned experiments, and has full administrative control over VMs in assigned experiments. E V E V V V V V
    VM Viewer Can only see VM screenshots and access VM VNC, nothing else. V

    Key: E - experiment resource, V - VM resource, U - user resource

    E* in the Experiment Admin row means the role can delete an experiment's files, but not the experiment itself.

    The built-in Builder role is for users of the Builder. It holds builder use, which gives access to the Builder and all its drafts, templates, layer sets and icons. It can also list, get, create, update and delete Topology, Scenario and Experiment configs, and can list, get, create and update experiments. Global Viewer does not have builder use. See the policies in Builder (builder) and The Builder role.

    Command Line¶

    On the phēnix server, the phenix admin commands manage users, custom roles and API tokens. The commands that change something go through the running phenix ui, as global-admin.

    # Create a user (it asks for the password twice)
phenix admin user create alice --role experiment-user --resource-names 'lab-*'

# Create a custom role
phenix admin role create "Lab Viewer" --policy 'resources=experiments,vms;verbs=list,get;names=lab-*'

    Use --password-stdin to pipe the password in instead.

    Manage Custom Roles Through the API¶

    A Global Admin can create, update and delete custom roles through the REST API (the roles resource); the built-in roles can't be changed or deleted. You can only hand out what you hold: the caller must hold each permission that the role gives, and a policy without resource names counts as a policy for *.

    To create a role, send POST /api/v1/roles with its name and policies:

    {
  "name": "Lab Operator",
  "metadataName": "lab-operator",
  "policies": [
    {"resources": ["experiments"], "verbs": ["list", "get"]},
    {"resources": ["vms", "vms/*"], "verbs": ["list", "get", "update"]}
  ]
}

    metadataName is optional. Without it, the config name is the name in lower case with other characters changed to -. Neither name can match another role's, ignoring case. A role can have up to 256 policies, and a policy up to 64 resources, 64 verbs and 64 resource names.

    To give the role to a user, send PATCH /api/v1/users/{username} with role_name and resource_names. You must hold each permission that the role gives with those resource names; permissions the user already holds don't count.

    PATCH /api/v1/roles/{name} replaces the policies of the role, and of each user's copy of it, with the complete new list (a role can't be renamed). Each user keeps the resource names they got with the role. If the old role had no policy without resource names, though, the new policies without resource names give the user no named resource: give the role to the user again to set the names. If some users can't be updated, the response is 500 with them in details.users; send the same request again.

    DELETE /api/v1/roles/{name} refuses a role that a user has (give them a different role first), or one that a default user in ui.users or the development key in ui.jwt-signing-key names.

    Resource: configs¶
    Verb list, get, create, update, delete
    Desc manage store configurations (topologies, scenarios, etc.)
    Exp. Scoped no
    Res. Scoped yes

    Resource names are <Kind>/<name>, such as Topology/riverside-water, not the name alone. Topology/* covers every topology, and */* covers every config, User and Role configs included (a * never crosses the /). phēnix also checks create and update against the kind and name of the config in the request body. So a role scoped to Topology/* cannot create or overwrite a User or Role config. An update that renames a config or changes its kind also needs create for the new Kind/name.

    The configs API never returns a User config's password hash or API tokens, and an update keeps the stored ones.

    Built-In Roles¶

    The following default roles are defined in phēnix as YAML resource specifications:

    Global Admin (global-admin)¶

    apiVersion: phenix.sandia.gov/v1
kind: Role
metadata:
  name: global-admin
spec:
  roleName: Global Admin
  policies:
  - resources:
    - "*"
    - "*/*"
    resourceNames:
    - "*"
    - "*/*"
    verbs:
    - "*"

    Global Viewer (global-viewer)¶

    apiVersion: phenix.sandia.gov/v1
kind: Role
metadata:
  name: global-viewer
spec:
  roleName: Global Viewer
  policies:
  - resources:
    - "*"
    - "*/*"
    resourceNames:
    - "*"
    - "*/*"
    verbs:
    - list
    - get
  - resources:
    - "vms/mount"
    resourceNames:
    - "*"
    - "*/*"
    verbs:
